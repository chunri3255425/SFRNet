# 鉴纹——基于 SFRNet 的翻拍攻击取证组件化安全中台（大创创意方案）

> 依据材料：`docs/literature/` 内 SFRNet 论文（ESWA 2027）、`TECHNICAL_DOC.md`（v2.0）、工程仓库实测记录。
> 方案定位：**放弃"一场景一方案"的写法，把项目重组为一套可插拔的安全取证组件平台**，主打安全类场景：远程身份核验、线上考试防作弊、人脸门锁防盗刷等。
> 文中技术数值均来自已有实测（TECHNICAL_DOC v2.0 / 论文 / 实机日志），不做外推。

---

## 一、一句话定位（对齐用）

> **SFRNet 能以 7.8M 参数、在 4K 超高清图像上逐像素感知"空间周期性异常"；而"摄像头拍屏幕必然产生摩尔纹"是一条物理定律。把这两者绑定，就得到一个不依赖硬件改造、不需要用户配合的被动取证能力——我们把它做成一组标准组件，插进任何需要"确认对面是真人、不是屏幕"的安全系统里。**

答辩压缩版：

> **别人做更准的活体检测，我们做更便宜的证据。一套 7.8M 参数的组件，回答所有安全系统共同的问题：这张脸/这个画面，是不是从另一块屏幕上来的。**

---

## 二、为什么"组件化"是正确方向（立项逻辑）

上一版方案（A~H）是"换数据换个场景"的横向铺开；本版改为**纵向平台化**，理由有三：

1. **工程底座已具备组件化雏形**。现仓库 `app/` 已是三层解耦（adaptation / logic_layer / model_layer），运行时后端天然多态（torch / onnx / rknn / rule / yolo 五种），Stage-1 YOLO 级联门 + Stage-2 滑窗推理 + Decider 三态判定（screen_detected / has_moire / no_moire）已经是标准化的"输入→判定→输出"流水线；`moireguard-console` 已有多设备管理 + SSE 视频流的设备墙雏形。**组件化不是从零开始，是把已做的事讲成一个更大的故事。**
2. **安全类场景共享同一个威胁模型**：黑产用第二台设备播放证件照/人脸视频/替考画面绕过活体与监考。物理机制相同（屏幕翻拍→差频摩尔纹）、判据相同（多帧一致性 + 覆盖率 + 主频）、工程接口相同（一帧图进、风险分出）。**一次研发，多场景复用**——这正是大创"创新训练"与"创业实践"都认可的平台叙事。
3. **评委叙事更聚焦**：原方案七个方向容易被批"多场景堆砌"；本版只有一条主线（翻拍攻击取证组件平台），其余场景是同一组件在不同安全业务里的"插装验证"，主线清晰、辐射面反而显得更大。

## 三、组件化架构设计（技术核心章节）

### 3.1 总体分层：一个内核 + 三类组件 + 一个控制台

```
┌─────────────────────────────────────────────────────────┐
│                鉴纹控制台（已有雏形）              │
│   设备墙 · 多实例管理 · SSE 实时视频流 · 三态告警展示       │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP /detect + SSE + gRPC(规划)
┌──────────────────────────▼──────────────────────────────┐
│                     取证服务组件（鉴纹 API）             │
│  ┌─────────┐  ┌──────────────┐  ┌────────────────────┐  │
│  │场景组件  │  │ 决策组件      │  │ 证据输出组件        │  │
│  │核验/考试 │  │ 多帧一致性    │  │ 风险分 + 掩膜 +     │  │
│  │门锁/终端 │  │ 双阈值分诊    │  │ 热力图 + JSON留痕   │  │
│  └─────────┘  └──────────────┘  └────────────────────┘  │
├──────────────────────────────────────────────────────────┤
│                    检测内核（鉴纹内核）                 │
│  Stage-1 YOLO 屏幕检测门 ─→ Stage-2 摩尔纹分割/规则图       │
│  （级联短路 · 灰区宁报不漏 · Hann 滑窗融合 · 唯一sigmoid）   │
├──────────────────────────────────────────────────────────┤
│              运行时适配层（多后端多态，已实现）              │
│   torch(开发机) / onnx / rknn(板端RK3576) / rule规则图     │
└──────────────────────────────────────────────────────────┘
```

### 3.2 内核组件（鉴纹内核）——直接复用现有资产

| 组件 | 现状 | 组件化改造 |
|---|---|---|
| 级联门 Stage-1（YOLO 屏幕检测） | 已实现，yolov8n 微调 v1 已训完 | 抽成独立组件包 `jianwen-gate`，阈值/灰区策略可配置 |
| 摩尔纹分割 Stage-2 | 已实现（滑窗 + Hann 融合） | 同上 `jianwen-moire`；输入分辨率/ tile/stride 参数化 |
| 判据引擎 | 板端已有零参数 DCT 规则图 `rule_v5.rknn`（阈值编译进 NPU 图） | 规则图按场景可换装——这是组件化里最有说服力的"可插拔判据"设计 |
| 运行时适配 | torch/onnx/rknn 五后端 | 统一 `RuntimeAdapter` 接口，部署形态自动选择 |

### 3.3 场景组件（鉴纹场景插件）——同一内核，不同插装

每个场景组件 = **数据微调包 + 决策策略包 + 对接适配包**，内核零改动或极小改动：

| 场景组件 | 威胁 | 特有决策策略 | 数据来源（自产闭环） |
|---|---|---|---|
| **S1 远程身份核验**（实面签） | 远程开户/认证中翻拍证件照、人脸视频 | 双阈值分诊：PASS / 疑似翻拍→追加活体动作 / 翻拍→人工复核。不否决交易，输出证据强度 | 3 部手机 × 2~3 块屏，自采 1000~2000 对 |
| **S2 线上考试防作弊** | 第二设备放在键盘旁/贴膜替考、手机直播给场外 | ROI 聚焦策略：对画面边缘/键盘区/眼镜反光区加权；连续 N 帧同区域报警才触发 | 校内模拟考场自采，考桌场景负样本 |
| **S3 人脸门锁防盗刷** | 用手机/平板播放主人照片视频骗过 2D 人脸门锁 | 低功耗策略：先有人脸检测再触发取证；板端 RKNN 全离线，数据不出门 | 手机拍门锁摄像头 + 门锁摄像头拍手机，双向采集 |
| **S4 自助终端/ATM 防翻拍**（拓展） | 在柜员机/政务终端前用手机翻拍他人证件操作 | 连拍 + 告警联动终端锁屏 | 情景摆拍 |
| **S5 视频客服/直播核身**（拓展） | 假人背景板、屏幕人脸冒充客服 | 多帧一致性 + 主频稳定性 | 直播场景自采 |

**组件化设计的三个答辩级亮点**：

1. **判据可换装**：规则图（`rule_v5.rknn`）把判据和阈值"烧"进 NPU 图，不同安全场景换不同规则图即完成"换判据"，无需重新部署整个模型链——这是把已知工程实践（编译期判据固化）重新诠释为组件化卖点；
2. **灰区分诊是安全业务的行业标准**：不输出硬判决，输出 `{PASS / SUSPECT / REPLAY}` 三态 + 风险分，对齐金融风控"升级人工复核/追加活体动作"的标准工作流——与"宁可放过绝不冤枉"的 Precision 优先价值取向（P=0.6286 / R=0.9942）自洽；
3. **多帧时序一致性是超越原论文的方法贡献**：单帧摩尔纹可能是衣物条纹等偶然干扰，连续帧在同一空间频点持续出现才是翻拍——把静态检测升级为时序检测，所有 S1~S5 共用。

## 四、三个主攻场景的业务论证

### S1 远程身份核验——"实面签"组件

- **业务锚点**：银行/券商/运营商远程开户、人社待遇资格认证、网络身份认证公共服务（反诈背景）。黑产翻拍绕过活体是真实、高频、有公开报道的攻击面。
- **定位（关键）**：**现有活体 SDK 的取证增强子模块，不是替代品**——不抢成熟厂商的饭碗，姿态安全，评委易认同。
- **演示设计（全场最有效）**：笔记本放人脸视频→手机对屏拍摄→大屏实时变红"Moiré Score 0.87 疑似翻拍"；镜头转真人→转绿 PASS。
- **合作方路径**：校信息办（考试/门禁试点）→ 本地银行网点科技部门 → 网安企业。

### S2 线上考试防作弊——"监考之眼"组件

- **业务锚点**：后疫情线上考试、教师资格/职业资格远程机考已成常态；替考最大破绽之一是第二屏幕的出现，而"画面里出现屏幕翻拍特征"是当前监考 AI 不看的信息。
- **独有改造（本组件的方法创新点）**：
  1. **区域加权 ROI**：作弊屏幕常出现在画面边缘、键盘反光区、眼镜反射中——复用 SFRNet 的像素级掩膜输出（这正是 4K 分割能力对检测框类方案的优势），按区域加权融合覆盖率；
  2. **低误报触发链**：YOLO 屏检门（Stage-1）与摩尔纹门（Stage-2）级联 + 连续 N 帧投票，单帧干扰不报警——直接复用已实现的级联架构，答辩时可以讲"我们的架构天生就是为低误报设计的"；
  3. **审计留痕**：每条告警附掩膜 + 热力图 + 风险分，供人工复核，符合考试违纪认定的证据要求。
- **合作方**：校内教务处/继续教育学院试点（成本≈0），再外推考试服务企业。

### S3 人脸门锁防盗刷——"门锁卫兵"组件

- **业务锚点**：2D 人脸门锁/闸机被手机视频骗过是安防行业公开痛点；高端方案用 3D 结构光（贵、需换硬件），我们提供**零硬件改造的软件补丁**——这是最打动设备的卖点：存量门锁升级，不动一颗螺丝。
- **落地形态（最贴项目现状）**：RK3576（Purple Pi OH2，6 TOPS NPU，整板 ¥999 + IMX415 ¥200）**全离线运行**，fp16 转换链已实测打通（板端与 onnxruntime 相关系数 1.0000）——"数据不出门、断网可用、5 瓦功耗"三个词全是加分项。
- **触发策略**：低功耗常态 → 人脸检测命中 → 才启动摩尔纹取证（复用 Stage-1 级联门思路），避免持续满载。
- **风险如实声明**：门锁是安防设备，申报书中定位为"门锁厂商的前置算法组件/评估样机"，不做整机销售，规避监管复杂度。

### 为什么"三个场景一起写"是对的（而非堆砌）

三者共享：同一威胁模型（屏幕翻拍）、同一内核、同一决策范式（三态分诊）、同一演示逻辑（对屏拍摄变红）。区别仅在 ROI 策略、触发链路、数据采集方式——**这恰好是组件化命题的证明**：写成一个平台，是结构；写成三个独立项目，才是堆砌。

## 六、创新点清单（申报书可直接取用）

1. **范式定位创新——"更便宜的证据"**：不与活体检测比精度，而是提供一条无硬件改造、无用户配合的被动取证通道，作为活体系统的增强子模块；
2. **架构创新——级联式低误报取证**：Stage-1 屏幕检测门（有屏短路、灰区宁报不漏）+ Stage-2 像素级摩尔纹分割 + 三态分诊决策，低误报结构内建于架构而非靠阈值拍脑袋；
3. **方法创新——多帧时序一致性判据**：从单帧静态检测升级为跨帧频点一致性检测，超越原论文范式；
4. **方法创新——MoE 路由坍缩的实证与修复**：负载均衡辅助损失 + 频率感知路由统计量，修复开源 SFRNet 条件计算退化（可出方法论短文/软著）；
5. **工程创新——判据编译进 NPU 的可换装规则图**：阈值与判据烘焙为 `rule.rknn`，按场景热插拔，配多后端运行时（torch/onnx/rknn）实现"一套内核、开发机到千元国产板全兼容"；
6. **平台创新——安全取证组件中台**：统一 API（帧进→风险分出）、统一控制台（设备墙 + SSE）、四类安全场景插装验证。

## 十、风险提示（如实写进申报书）

| 风险 | 应对 |
|---|---|
| 单帧误报（衣物条纹/背景图案） | 级联门 + 多帧一致性 + 三态分诊，宁可升级人工复核不硬拦 |
| 各场景域差异（考场/门锁光照角度不同） | 场景组件自带微调数据包，内核参数冻结只换数据与策略 |
